# Feature Implementation

**원칙: 정책이 확정되고 설계가 승인되기 전에는 소스 코드를 수정하지 않는다.**
경로는 모두 이 SKILL.md가 있는 디렉터리 기준 상대 경로다.

## 0. 규모 판단

| 규모 | 기준 | 진행 |
|---|---|---|
| 경량 | 1~3개 파일, 정책·데이터 모델·API 계약 변경 없음 | 1~5단계를 대화 안에서 짧게(설계 5줄 요약) → 승인 → 구현 → 요약. 문서 파일 생략 가능 |
| 표준 | 그 외 전부 | 모든 단계 수행, `DESIGN.md`·`SUMMARY.md` 작성 |

애매하면 표준으로 한다. 사용자가 "설계 없이 바로 해줘"라고 명시하면 경량으로 진행하되, 불명확한 정책은 가정으로 드러내고 요약에 남긴다.

## 작업 폴더

```bash
mkdir -p .design/<YYYYMMDD>-<slug> && printf '*\n' > .design/.gitignore
```
`.design/`는 커밋되지 않는다. 팀이 설계 문서를 커밋하는 관례(`docs/design/` 등)가 있으면 위치를 사용자에게 묻는다.

## 1. 요구사항 정리
- 요청을 한 문단으로 다시 서술하고 **목표**와 **비목표**(이번에 하지 않는 것)를 나눈다.
- **성공 기준**: 어떤 입력·상황에서 어떤 결과가 나오면 완료인지, 테스트로 옮길 수 있는 형태로 적는다.
- 참고한 티켓·문서·대화를 기록한다.

## 2. 정책 명확성 점검
`references/policy-checklist.md`의 항목별로 판정한다. 해당 없는 항목은 생략한다.

| 판정 | 의미 | 필요한 것 |
|---|---|---|
| ✅ 명확 | 요구사항이나 기존 코드에 정해져 있음 | 근거 (요구사항 문장, `path:line`) |
| ❓ 불명확 | 정할 수 없고 결과에 영향을 줌 | 질문 (선택지 + 추천안) |
| ⚠️ 가정 | 합리적 기본값이 있음 | 제안한 기본값, 사용자 확인 |

- 유사 기능에 이미 구현된 규칙(검증, 권한, 상태 전이)은 근거로 쓸 수 있다.
- 새 요구사항이 기존 정책과 **충돌**하면 반드시 ❓로 올린다.

## 3. 코드베이스 맥락 파악
- `.onboarding/ONBOARDING.md`가 있으면 먼저 읽는다. 없는데 레포가 낯설면 `repo-onboarding` quick 모드를 제안한다.
- `references/conventions.md`에 따라 **가장 비슷한 기존 기능 1~2개를 레퍼런스로 정하고** 패키지 구조, 네이밍, 계층 간 책임, 예외·응답·테스트 방식을 추출한다.
- 영향 범위: 변경할 코드의 호출부, 같은 테이블·토픽·캐시를 쓰는 곳, 깨질 수 있는 기존 테스트.
- 스택별 탐색: `../repo-onboarding/references/stacks/java-spring.md`, `../repo-onboarding/references/stacks/dotnet.md`

## 4. 구현 설계
`templates/DESIGN.md`를 채운다. 반드시 들어가야 할 것:
- 레퍼런스 기능과 따를 컨벤션
- 변경 파일 목록(신규/수정). 위치는 기존 패키지 구조를 따른다.
- API 계약(요청·응답·에러코드)과 하위 호환성
- 데이터 변경: 스키마, 마이그레이션, 기존 데이터 처리. 스키마가 바뀌면 `references/db-migration.md`를 적용해 호환성, 배포 순서, 락 영향, 롤백 전략을 적는다.
- 트랜잭션 경계, 동시성·멱등성, 외부 연동 실패 처리
- 테스트 계획 (프로젝트의 테스트 스타일과 계층)
- 구현 순서 (각 단계가 컴파일·테스트로 검증 가능하게 작게)
- 의미 있는 대안이 있었다면 선택 이유

## 5. 확인 요청 — 구현 게이트
사용자에게 **한 번에** 제시한다.
1. ❓ 질문 — 답에 따라 설계가 달라지는 것부터. 선택지와 추천안을 함께 준다.
2. ⚠️ 가정 목록
3. 설계 요약 — 변경 파일, 핵심 결정, 테스트 계획

**구현 시작 조건 (Definition of Ready)** — 모두 충족해야 6단계로 간다.
- [ ] 모든 ❓에 답이 있거나, 사용자가 해당 가정을 승인했다
- [ ] 사용자가 설계를 명시적으로 승인했다 ("진행해", "OK" 등)
- [ ] 성공 기준과 테스트 계획에 합의했다

답을 받으면 `DESIGN.md`의 결정 이력에 기록하고, 설계가 바뀌었으면 바뀐 부분만 다시 요약해 확인받는다.
조건을 충족하기 전에는 소스·설정·마이그레이션 파일을 수정하지 않는다. 조회, 빌드, 기존 테스트 실행은 해도 된다.

## 6. 구현
- `DESIGN.md`의 구현 순서대로 작게 진행하고, 단계마다 컴파일과 관련 테스트를 돌린다.
- **컨벤션**: 레퍼런스 기능과 같은 구조·네이밍·패턴으로 작성한다. 새 라이브러리, 새 패턴, 새 계층이 필요해 보이면 멈추고 묻는다.
- **가독성**: `references/readable-code.md`를 따른다. 주석은 코드로 표현할 수 없는 "왜"에만 단다.
- **범위**: 설계에 없는 리팩토링, 이름 변경, 포맷 변경은 하지 않는다. 발견한 문제는 요약의 후속 작업에 적는다.
- 구현 중 새로운 정책 질문이나 설계 변경이 생기면 **멈추고** 확인받은 뒤 `DESIGN.md` 결정 이력에 남긴다.

## 7. 검증
- 빌드, 테스트(신규 + 영향받는 기존), 프로젝트의 린트·포맷터(spotless, checkstyle, ktlint, `dotnet format` 등)를 실행한다.
- 실패를 숨기지 않는다. 실행하지 못한 검증은 이유와 함께 보고한다.

## 8. 리뷰
1. **셀프 정리**: 전체 diff를 다시 읽고 디버그 코드, 사용하지 않는 코드, 불필요한 주석, 설계 밖 변경을 먼저 걷어낸다.
2. **독립 리뷰**: `impl-review` 스킬로 구현 맥락이 없는 리뷰어에게 리뷰받는다. 경량 규모는 생략할 수 있다.
   - 🔴·🟠 지적은 반영하고 7단계 검증을 다시 실행한다.
   - 반영하려면 설계나 정책을 바꿔야 하는 경우 멈추고 사용자에게 묻는다.

## 9. 핵심 구현 요약
`templates/SUMMARY.md`를 채워 저장하고, 대화에는 다음을 보고한다.
- 무엇을 구현했는지 (3줄 이내)
- 핵심 변경 (`path:line` + 한 줄 설명)
- 주요 결정과 설계 대비 달라진 점
- 검증 결과 (실행한 명령과 결과, 실행하지 못한 것)
- 독립 리뷰 결과 (반영한 지적, 보류한 지적과 이유)
- 리뷰어가 집중해서 볼 곳, 후속 작업
