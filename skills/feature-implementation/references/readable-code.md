# 읽기 쉬운 코드 가이드

코드는 이름과 구조로 스스로 설명해야 한다. 주석은 코드로 표현할 수 없는 **"왜"**에만 쓴다.
아래 원칙이 프로젝트 관례와 충돌하면 프로젝트 관례를 따른다.

## 이름
- 도메인 용어를 그대로 쓴다(`.onboarding/GLOSSARY.md`가 있으면 참고). 같은 개념에는 같은 이름을 쓴다.
- 축약하지 않는다: `ordCnt` → `orderCount`
- boolean은 `is`/`has`/`can`으로 시작하고, 메서드 이름은 동사로 시작한다. 이름이 길어지는 것은 괜찮다.

## 함수와 구조
- 함수 하나는 한 가지 일을, 한 가지 추상화 수준으로 한다.
- 조기 반환(guard clause)으로 중첩을 줄인다.
- 복잡한 조건식은 의도를 드러내는 메서드나 변수로 뽑는다.
- 매직 넘버와 문자열은 상수나 enum으로 바꾼다.
- **과도한 추상화를 피한다**: 구현체가 하나뿐인 인터페이스, 한 번만 쓰는 제네릭 유틸, "나중을 위한" 확장 포인트는 프로젝트 관례일 때만 만든다.

```java
// Before
if (order != null && order.getStatus() == Status.PAID && order.getPaidAt().plusDays(7).isAfter(now)) { ... }

// After
if (order.isRefundableAt(now)) { ... }
```

## 주석 정책
| 쓴다 | 쓰지 않는다 |
|---|---|
| 비즈니스 정책의 근거 (`// 전자상거래법상 7일 이내 청약철회 가능`) | 코드를 다시 말하는 주석 (`// 사용자 조회`) |
| 직관에 반하는 결정의 이유 | 변경 이력 (`// 2024-03 홍길동 수정`) — git이 한다 |
| 외부 시스템 제약이나 우회 (`// PG사 API가 동일 키 재요청 시 200을 반환함`) | 주석 처리된 코드 |
| 공개 API 문서가 프로젝트 관례일 때 (Javadoc, XML doc) | 모든 메서드에 기계적으로 붙이는 Javadoc/`<summary>` |
| 티켓이 연결된 TODO (`// TODO(ORD-123): ...`) | 섹션 구분 배너, 티켓 없는 TODO |

```csharp
// Before
// 주문 상태를 취소로 변경한다
order.Status = OrderStatus.Cancelled;

// After — 주석 없이 이름으로 설명하고, 필요한 "왜"만 남긴다
order.Cancel();   // 정산 배치가 상태만 보고 환불하므로 금액은 여기서 바꾸지 않는다
```

## 에러 처리
- 예외를 삼키지 않는다. 잡았으면 처리하거나, 맥락을 붙여 다시 던진다.
- 프로젝트의 예외 체계와 에러코드를 쓴다. 범용 `RuntimeException`/`Exception`을 새로 던지지 않는다.
- 예외 메시지에는 원인 파악에 필요한 식별자를 넣고, 개인정보는 넣지 않는다.

## 로그
- 레벨: 운영자가 조치해야 하면 `ERROR`, 비정상이지만 복구됐으면 `WARN`, 비즈니스 이벤트는 `INFO`, 나머지는 `DEBUG`
- 개인정보와 시크릿은 남기지 않는다. 프로젝트의 로거와 메시지 형식을 쓴다.

## 테스트 코드
- 테스트 이름이 시나리오를 설명해야 한다 (프로젝트의 이름 규칙을 따름).
- given / when / then 구조로 쓰고, 한 테스트는 한 가지 행위만 검증한다.
- 테스트에서도 의미 없는 값 대신 의도가 드러나는 fixture를 쓴다.
