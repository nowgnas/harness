# DB 마이그레이션 안전 가이드

스키마 변경은 코드 변경보다 되돌리기 어렵다.
롤링 배포 중에는 **구버전 코드와 신버전 코드가 같은 스키마를 동시에 쓴다**는 전제로 설계한다.

## 1. 기본 규칙
- 스키마는 마이그레이션 도구로만 바꾼다. 도구 없이 DBA가 DDL을 적용하는 조직이면 DDL 스크립트와 적용 요청서를 산출물로 만든다.
- 이미 머지되었거나 적용된 마이그레이션은 수정하지 않는다. 새 마이그레이션을 추가한다.
- 한 마이그레이션에는 한 가지 목적만 담는다. DDL과 대량 DML을 섞지 않는다.
- 운영 설정에서 `spring.jpa.hibernate.ddl-auto`는 `validate` 또는 `none`이어야 한다(`update` 금지).
- EF Core에서 앱 시작 시 `Database.Migrate()`를 자동 실행하면 여러 인스턴스가 동시에 실행할 위험이 있다. 이 방식을 쓰는지 확인한다.
- 로컬에서 적용하고, 앱을 기동하고, 테스트까지 통과하는 것을 확인한다.

| 도구 | 주의점 |
|---|---|
| Flyway | `V<버전>__<설명>.sql` 명명 규칙. 병렬 브랜치 사이의 버전 번호 충돌과 `outOfOrder` 설정을 확인한다. 트랜잭션 안에서 실행할 수 없는 DDL(PostgreSQL `CONCURRENTLY` 등)은 파일을 분리한다(비트랜잭션 실행 지원 여부는 Flyway 버전별로 확인) |
| Liquibase | changeSet의 `id`+`author`는 바꾸지 않는다. `runOnChange`에 주의하고, 관례라면 `rollback` 블록과 preconditions를 작성한다 |
| EF Core | `dotnet ef migrations add` 결과 코드와 **생성된 SQL**(`dotnet ef migrations script <from> <to>`)을 반드시 검토한다. 컬럼 이름 변경이 drop+add로 생성되지 않았는지, ModelSnapshot 머지 충돌이 없는지 확인한다 |
| 수동 SQL (MyBatis 등) | `db/`, `sql/` 폴더 관례와 적용 이력 관리 방식을 확인하고, 모르면 질문한다 |

## 2. 호환성: Expand → Migrate → Contract
파괴적인 변경은 한 번의 배포로 끝내지 않는다.

| 변경 | 안전한 순서 (→ 는 별도 배포) |
|---|---|
| 컬럼 추가 | nullable이거나 기본값이 있는 컬럼을 추가하고 코드를 배포한다. NOT NULL은 백필한 뒤 별도 단계에서 건다 |
| 컬럼 이름·타입 변경 | 새 컬럼 추가 → 양쪽에 쓰는 코드 → 백필 → 새 컬럼에서 읽기 → 구 컬럼 쓰기 중단 → 구 컬럼 삭제 |
| 컬럼·테이블 삭제 | 코드와 ORM 매핑에서 사용을 제거하고 배포 → 다음 배포에서 삭제 |
| NOT NULL 추가 | 코드가 항상 값을 채우도록 배포 → 백필 → 제약 추가 |
| enum·코드 값 추가 | 구버전 코드가 새 값을 읽으면 실패하는지 확인한다(Java `Enum.valueOf`, JSON 역직렬화). 읽는 쪽을 먼저 배포한다 |
| 유니크·FK·CHECK 제약 추가 | 기존 데이터 중 위반하는 건수를 먼저 조회한다 |

설계에는 두 조합이 모두 동작하는지(**새 코드 + 구 스키마**, **구 코드 + 새 스키마**)와 **배포 순서**(DB 먼저 / 앱 먼저)를 명시한다.

## 3. 락과 대용량 테이블
행이 많거나 트래픽이 많은 테이블의 DDL은 락 때문에 장애를 일으킬 수 있다.
동작은 DB 종류, 버전, 에디션마다 다르므로 **공식 문서로 확인한 뒤** 설계에 근거와 함께 적는다.

| DB | 확인할 것 |
|---|---|
| MySQL (InnoDB) | Online DDL의 `ALGORITHM=INSTANT/INPLACE`와 `LOCK=NONE` 지원 여부는 연산과 버전마다 다르다. 명시해 두면 지원하지 않을 때 에러로 멈춘다. 긴 트랜잭션이 있으면 metadata lock 대기가 생기고 뒤따르는 쿼리가 줄줄이 막힌다. 대형 테이블은 gh-ost나 pt-online-schema-change를 검토한다 |
| PostgreSQL | 인덱스는 `CREATE INDEX CONCURRENTLY`로 만든다(트랜잭션 밖에서만 가능). NOT NULL·FK·CHECK는 `NOT VALID`로 추가한 뒤 `VALIDATE`한다. 마이그레이션 세션에 `lock_timeout`을 설정한다. volatile 기본값을 가진 컬럼을 추가하면 테이블이 재작성된다 |
| SQL Server | 온라인 인덱스 작업(`ONLINE = ON`)은 에디션 제약이 있다. 스키마 수정 락(Sch-M) 대기에 주의한다. 기본값이 있는 컬럼 추가 동작은 버전·에디션별로 확인한다 |
| Oracle | 인덱스 `ONLINE` 옵션과 기본값 컬럼 추가 동작을 버전별로 확인한다 |

- 인덱스: 새 쿼리의 실행 계획(EXPLAIN)을 확인하고, 삭제하려는 인덱스를 기존 쿼리가 쓰고 있지 않은지 확인한다.
- 대상 테이블의 행 수를 조회해 예상 소요 시간을 추정하고, 적용 시간대와 함께 설계에 적는다.

## 4. 데이터 변경 (백필·보정)
- 대량 UPDATE·DELETE는 마이그레이션 파일에 넣지 않는다. 배치나 스크립트로 분리하고, PK 범위로 나눠 커밋한다.
- 스크립트는 멱등하게 작성한다(예: `WHERE new_col IS NULL`). 실행 전 대상 건수를 확인하는 쿼리를 함께 제공한다.
- **운영 실행은 사람이 한다.** 에이전트는 스크립트와 검증 쿼리까지만 만든다.

## 5. 롤백
- 대부분의 복구는 되돌리는 마이그레이션보다 **앞으로 고치는 것**(forward fix)이다. 설계에 롤백 전략을 적는다.
  - 앱만 롤백해도 되는가? (expand 단계라면 가능)
  - 데이터가 사라지는 변경(삭제, 타입 축소)이라면 백업(테이블 복사)을 하는가?
- Liquibase `rollback`이나 EF `Down()`을 작성하는 것이 레포 관례라면 따른다.

## 6. 체크리스트 (설계·리뷰 시)
- [ ] 마이그레이션 도구와 파일 규칙을 지켰고, 기존 마이그레이션을 수정하지 않았다
- [ ] 구 코드 + 새 스키마, 새 코드 + 구 스키마가 모두 동작한다
- [ ] 배포 순서를 명시했다
- [ ] 대상 테이블 크기와 락 영향을 DB 종류·버전 기준으로 확인했다
- [ ] 제약을 추가하기 전에 기존 데이터의 위반 건수를 확인했다
- [ ] 대량 DML을 분리했고 스크립트가 멱등하다
- [ ] 엔티티·모델 매핑이 스키마와 일치한다 (ddl-auto validate, EF snapshot)
- [ ] 새 쿼리의 인덱스와 실행 계획을 확인했다
- [ ] 롤백 전략이 있다
- [ ] 로컬에서 적용 → 앱 기동 → 테스트까지 확인했다
