# Bug Fix

**원칙: 원인을 입증하기 전에는 고치지 않는다.**
널 체크 추가, 예외 삼키기, 재시도 추가처럼 증상만 가리는 수정은 그것이 실제 원인에 대한 해법일 때만 한다.
경로는 모두 이 SKILL.md가 있는 디렉터리 기준 상대 경로다.

## 1. 증상 정리
- 기대 동작과 실제 동작, 에러 메시지·스택트레이스
- 발생 환경(로컬/개발/운영), 시작 시점, 빈도(항상/간헐), 영향 범위(사용자, 데이터)
- 코드, 로그, git 이력으로 알 수 있는 것은 직접 확인하고, 나머지만 질문한다.
- 운영 장애가 진행 중이면 원인 분석보다 **완화**(롤백, 기능 플래그 끄기)를 먼저 제안한다.

## 2. 재현
아래 순서로 시도한다.
1. **실패하는 자동 테스트** (단위 테스트가 가능하면 단위, 아니면 통합). 프로젝트의 테스트 스타일을 따른다.
2. 로컬 실행 후 요청 (curl, `.http` 파일)
3. 재현이 안 되면 로그, 데이터, 코드 경로로 발생 조건을 논리적으로 입증하고 "재현 안 됨"을 명시한다.

재현 테스트를 추가하는 것은 진단으로 보고 4단계 게이트 전에도 허용한다. 추가했다면 사용자에게 알린다.

## 3. 원인 분석
- 스택트레이스에서 가장 깊은 **자기 코드** 프레임부터 본다.
- 가설을 표로 관리한다: 가설 | 근거 | 반증 방법 | 결과(채택/기각). 하나씩 제거한다.
- 회귀가 의심되면 이력을 추적한다.
  ```bash
  git log --oneline --since='2 weeks ago' -- <의심 파일>
  git log -p -S'<심볼>' -- <경로>
  git bisect start <나쁜 커밋> <좋은 커밋> && git bisect run <재현 테스트 명령>
  ```
- 흔한 원인 목록: `references/common-causes.md`
- "왜 이 입력에서 이 코드가 이렇게 동작하는가"를 `path:line`으로 설명할 수 있어야 원인을 **확정**한 것이다.
- 같은 원인이 다른 곳에도 있는지 검색한다(같은 패턴을 복사해 쓴 코드).

## 4. 수정 계획 — 게이트
다음을 보고한다: 원인(근거), 재현 방법, 수정 방향(대안이 있으면 비교), 영향 범위, 기존 데이터 영향.

아래 중 **하나라도 해당하면 승인을 받은 뒤** 수정한다.
- 동작이나 정책이 바뀐다 (현재 동작에 의존하는 곳이 있을 수 있음)
- API 계약이나 DB 스키마가 바뀐다
- 데이터 보정이 필요하다
- 수정 범위가 3개 파일을 넘는다
- 원인을 확정하지 못해 추정으로 수정한다

해당하는 것이 없으면 계획을 보고하고 바로 수정해도 된다. 단, 사용자가 확인 후 진행을 원하면 기다린다.
정책 판단이 필요하면 `../feature-implementation/references/policy-checklist.md`를 쓴다.

## 5. 수정
- 원인 지점을 최소 범위로 고친다. 프로젝트 컨벤션과 `../feature-implementation/references/readable-code.md`를 따른다.
- 원인과 무관한 리팩토링은 하지 않는다. 같은 패턴의 다른 발생 지점은 보고한 뒤 결정을 받는다.
- 스키마를 바꿔야 하면 `../feature-implementation/references/db-migration.md`를 따른다.

## 6. 검증
- 재현 테스트가 실패하다가 통과하는지, 관련 기존 테스트, 빌드, 린트를 확인한다.
- 재현 테스트는 회귀 방지용으로 남긴다.

## 7. 영향 데이터
- 버그 때문에 잘못 저장된 데이터가 있을 수 있는지 확인한다.
- 있으면 대상을 찾는 조회 쿼리와 보정 스크립트 **초안**을 만든다. 스크립트는 멱등하게, 건수 확인과 트랜잭션을 포함해서 작성한다.
- **실행은 사람이 한다.** 에이전트는 운영 데이터에 쓰지 않는다.
- 잘못 발행된 이벤트나 이미 실행된 외부 호출이 있었는지도 확인한다.

## 8. 리뷰
경량 수정(1~3개 파일, 동작 변경 없음)이 아니면 `impl-review` 스킬로 독립 리뷰를 받는다.

## 9. 요약
`templates/BUGFIX.md`를 채워 `.design/<YYYYMMDD>-bug-<slug>/BUGFIX.md`에 저장한다.
`.design`이 없으면 먼저 `mkdir -p .design/<...> && printf '*\n' > .design/.gitignore`를 실행한다.

대화에는 다음을 보고한다.
- 원인 한 줄
- 수정 내용 (`path:line`)
- 검증 결과
- 데이터 영향
- 재발 방지 제안
