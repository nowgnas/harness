# Personal Harness — Core Rules (Backend)

이 규칙은 개인 하네스(`harness` 레포)에서 모든 에이전트에 공통으로 주입된다.

## 작업 원칙
- 사용자에게는 한국어로 답한다. 코드·식별자·커밋 메시지는 레포 관례를 따른다.
- 코드를 바꾸기 전에 먼저 읽는다. 호출부·테스트·설정까지 확인하고 나서 수정한다.
- 레포의 기존 컨벤션(패키지 구조, 네이밍, 예외 처리, 로깅 방식)을 새 스타일보다 우선한다.
- 주장에는 근거를 붙인다: `path/to/File.java:42`. 확인하지 못한 내용은 `(추정)`으로 표시한다.

## 코드 작성 원칙
- 프로젝트의 코드 컨벤션, 패키지 구조, 개발 방법론(레이어드/헥사고날/DDD/CQRS)을 따른다. 가장 비슷한 기존 기능을 레퍼런스로 삼는다.
- 읽기 쉬운 코드를 쓴다: 의도를 드러내는 이름, 작은 함수, 조기 반환. 필요 없는 추상화는 만들지 않는다.
- 주석은 코드로 표현할 수 없는 "왜"에만 단다. 코드를 다시 설명하는 주석, 변경 이력, 주석 처리된 코드는 남기지 않는다.
- 요청 범위 밖의 리팩토링·포맷 변경은 하지 않는다. 발견한 문제는 따로 보고한다.

## 백엔드 안전 규칙
- DB 스키마 변경은 마이그레이션 파일(Flyway/Liquibase/EF Migrations)로만 한다. 기존 마이그레이션은 수정하지 않는다.
- 트랜잭션 경계, 동시성, 멱등성, 재시도에 영향을 주는 변경은 사용자에게 명시적으로 알린다.
- 설정 파일의 시크릿 값(비밀번호, 토큰, 연결 문자열)은 출력하지 않는다. 키 이름만 언급한다.
- 운영/공유 환경(DB, 메시지 브로커, 클라우드)에 쓰기 작업을 하지 않는다. 필요하면 명령만 제안한다.

## 하네스 스킬
- `repo-onboarding` — 처음 보는 레포/프로젝트 파악. 결과는 대상 레포의 `.onboarding/`에 저장.
- `feature-implementation` — 기능 구현. 정책 점검 → 설계 → 승인 후 구현 → 검증 → 요약. 결과는 `.design/`에 저장.
- `trace-flow` — API 엔드포인트·메시지·배치 하나를 진입점부터 DB/외부 호출까지 추적.
- `harness-install` — 하네스를 글로벌/프로젝트에 설치·업데이트·제거.
